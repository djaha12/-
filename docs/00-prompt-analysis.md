# ATELIER — Фаза 0: анализ промпта

Статус: на утверждении у Dars. Ни одной строки кода до «поехали».

## 1. Противоречия и риски в ТЗ

### 1.1 Антинакрутка vs холодный старт (критично)
«Отзыв только по завершённому заказу внутри платформы» — правильно в долгую, но в день запуска
ни у кого нет ни одного отзыва: витрина сравнения пуста, рейтинги бессмысленны, платформа выглядит мёртвой.
Нужна стратегия холодного старта (см. вопрос №5): либо строго «только верифицированные» + консьерж-онбординг
реальных специалистов, либо импортированные отзывы с явной меткой «не подтверждён платформой».

### 1.2 «Отзыв только по заказу» не закрывает накрутку полностью
Схема переносит фрод с «написать фейковый отзыв» на «создать и завершить фейковый заказ» — это дороже,
но бесплатно, т.к. платёжных механик нет (принципиально). Дизайн-контрмеры:
- заказ создаётся только при взаимном подтверждении двух верифицированных телефонов;
- переход «сдан» предлагает специалист, подтверждает клиент (или авто-подтверждение через N дней с уведомлением);
- чек-поинты с фотофиксацией повышают вес отзыва («отзыв с историей работ» ранжируется выше);
- velocity-лимиты и аномалии (N заказов между одними и теми же аккаунтами) — в очередь модерации;
- вес отзыва зависит от верификации клиента.

### 1.3 Премодерация vs «кейс с телефона за 5 минут»
Полная премодерация убивает момент радости публикации. Решение — trust-tiers:
- новый аккаунт: первые 2–3 кейса через премодерацию + автопроверки (NSFW, pHash-дубликаты внутри платформы);
- верифицированный/зарекомендовавший себя: публикация сразу, пост-модерация по жалобам и автофлагам.

### 1.4 Instagram-импорт: API-реальность
Basic Display API закрыт (дек. 2024). Graph API работает только для business/creator-аккаунтов и требует app review.
Скрейпинг — нарушение ToS и постоянные поломки. Фазируем:
- MVP: превосходная ручная загрузка с телефона (мультизагрузка, черновики, автосейв) + «вставь ссылки на посты»
  как структурирующий помощник (подписи/порядок руками);
- Фаза 1.5: OAuth-импорт через Graph API для business/creator (большинство специалистов КР такие).

### 1.5 Платёжки КР: мерчант-договоры — недели
Mbank / O!Деньги / Элсом / Balance.kg требуют юрлицо и договоры. На старте:
абстракция PaymentProvider + PRO через ручную активацию/промокоды админом; интеграции — как только будут доступы.

### 1.6 «Портфолио-сайт на своём домене» — тяжёлая мультитенантность
Wildcard TLS, host-based routing, изоляция. В Фазе 1 — красивый публичный профиль `/{username}`
и «режим витрины» (минимум хрома); архитектура роутинга готова к кастомным доменам, сами домены — Фаза 2.

### 1.7 Дезинтермедиация
Без комиссий удержание пар «клиент-специалист» на платформе = только ценность репутации.
Специалисты будут выкладывать контакты в кейсах. Нужна политика контактов (вопрос №7).

### 1.8 PWA push на iOS ограничен
Работает только после установки на домашний экран (iOS 16.4+). Telegram — основной канал (совпадает с ТЗ),
поэтому привязка Telegram (deep-link `t.me/bot?start=token`) — first-class шаг онбординга, а не опция в настройках.

## 2. Пробелы (чего нет в ТЗ — добавляем)

- **Профиль клиента** не описан. Предлагаю минимум: имя, аватар, город, коллекции; публично — «на платформе с…,
  N завершённых заказов» (лёгкая репутация клиента для специалистов, без оценок клиентов в MVP).
- **Агентства**: модель организаций (org, membership, роли) — в ERD с первого дня, полноценный UI — после MVP;
  в MVP специалист указывает «работает в X».
- **State machine заказа неполная**: добавить `отменён` (кем/почему), `спор` (арбитраж админом),
  правила взаимных подтверждений и авто-переходов. Отдельная схема в блоке ERD.
- **Матрица уведомлений**: событие → каналы (in-app центр = источник истины; Telegram; push). Настройки пользователя.
- **EXIF/GPS**: фото интерьеров содержат геометки домов клиентов — приватность. sharp при перекодировании
  срезает метаданные — фиксируем как требование пайплайна.
- **Аналитика и фиче-флаги — buy, не build**: PostHog (events, funnels, retention, flags) + тонкий внутренний
  дашборд доменных метрик (воронка заказов). Ручная реализация всего этого — недели работы не по делу.
- **OTP-экономика**: SMS в КР дорогие и капризные. Предложение: Telegram Gateway (официальный, дешёвый,
  регион живёт в Telegram) как первичный канал OTP + SMS-fallback через местного агрегатора (вопрос №2).
- **Хостинг не задан** (вопрос №1). Дефолт: Hetzner VPS + Docker Compose, Cloudflare CDN, R2 для изображений
  (нулевой egress), Postgres на VPS с ежедневными бэкапами в R2 + staging-стенд. ~$50–80/мес.
- **Курс сом→USD**: официальный API НБКР, кэш сутки, хранится в БД (ExchangeRate).
- **SEO-i18n**: канонические страницы профилей/кейсов на русском (поисковый спрос «дизайнер интерьера Бишкек» —
  русскоязычный), hreflang на ky/en, латинские слаги, транслитерация.
- **Краденые портфолио**: MVP — pHash-дедупликация внутри платформы + жалобы; внешний реверс-поиск —
  вручную модератором (API TinEye/Vision — платно, Фаза 2).
- **Seed ≠ продакшен**: 40 специалистов / 120 кейсов — для dev/staging/демо. Запуск в проде — консьерж-онбординг
  30–50 реальных специалистов Бишкека (GTM, вне кода, но влияет на приоритет онбординг-мастера).
- **Юр. база**: оферта/политика — шаблоны с ревью юристом до запуска; локализация перс. данных для Узбекистана —
  чек-пункт Фазы 2 (в УЗ требование локализации данных граждан).

## 3. Технические решения (предлагаю, утверждается с планом)

- **Монорепо** pnpm + Turborepo: `apps/web` (Next.js 15 App Router), `apps/services` (Fastify: WebSocket-чат,
  BullMQ-воркеры на Redis, Telegram-бот grammY), `packages/db` (Prisma), `packages/core` (доменная логика,
  чистый TS — тестируемые правила: отзыв только после заказа, лимиты Free), `packages/i18n`, `packages/config`.
- **Backend = Next.js, не NestJS**: SSR-колокация (SEO — обязательное требование), типы край-в-край без дублирования
  DTO, один фреймворк меньше при команде из одного агента. Длинноживущие процессы (WS, очереди, бот) физически
  не живут в Next — для них отдельный лёгкий сервис. NestJS дал бы структуру, но ценой второго HTTP-слоя
  под SSR и двойного бойлерплейта — «удобство vs скорость» тут не конфликтует: страдала бы и скорость, и SSR-UX.
- **API**: tRPC поверх Route Handlers (интеграция с TanStack Query из коробки, переиспользуется в будущем
  React Native из того же монорепо); чистые REST-хендлеры только для вебхуков (Telegram, платёжки) и OG-изображений.
- **Поиск: Meilisearch** (типо-толерантность из коробки — критично для смешанного ру/кыр ввода, фасеты, geo,
  single-binary — проще в эксплуатации на VPS). Через абстракцию SearchService — заменяем без переделок.
- **Изображения**: загрузка → sharp: EXIF-strip, варианты 400/800/1600 в AVIF+WebP, blurhash в БД → R2 → Cloudflare CDN.
- **Скриншот-доказательства**: Playwright предустановлен в среде; свой харнесс `pnpm shots` —
  1440px и 390px × light/dark по списку маршрутов, вывод в `screenshots/` для design-reviewer. MCP не требуется.
- Skill `frontend-design` в окружении отсутствует — его роль выполняют `.claude/skills/atelier-conventions`
  (дизайн-система, чек-листы экранов) + субагент design-reviewer. Создаём в блоке бутстрапа.
