# Ревью UX-драфтов: кросс-сверка клиент ↔ специалист ↔ агентство/админ

Статус: ревью выполнено. Проверялись `ux-client.md`, `ux-specialist.md`, `ux-agency-admin.md`
между собой и против `04-product-spec.md` / `03-decisions.md` / `00-prompt-analysis.md`,
с опорой на `schema.prisma`, `data-model-notes.md`, `api-contract.md`, `events-notifications.md`.

Оси проверки: (1) стыковка сценариев клиент↔специалист; (2) терминология;
(3) регистрация в момент ценности; (4) мобильная эргономика; (5) пусто/ошибка/офлайн;
(6) консистентность аналитики.

## Находки

### 1. [blocker] Кейсы, приложенные к отклику, не существуют в данных — сравнение профилей теряет ключевой контент
- **Файлы**: `ux-specialist.md` §Сценарий 3, шаг 4 и S14; `ux-client.md` §Сценарий 2, шаг 5; `schema.prisma` (BriefResponse); `api-contract.md` §11 `briefs.respond`.
- **Суть**: специалист «выбирает 1–3 кейса из портфолио» в отклик (и аналитика уже считает `cases_attached_count`), клиент в сравнении видит «3 кейса в стиле референсов». Но `BriefResponse` содержит только `message` + `priceEstimate`; `briefs.respond` кейсы не принимает; `briefs.responses` их не отдаёт. Стыковка «отклик специалиста = карточка в сравнении клиента» рвётся: главный визуальный аргумент выбора не доезжает.
- **Исправление**: добавить связку кейсов к отклику (join-таблица `BriefResponseCase` или `caseIds: string[](..3)` во входе `briefs.respond`), отдавать их в `briefs.responses`. В `ux-client.md` §2 шаг 5 уточнить: в сравнении показываются кейсы, приложенные специалистом к отклику (авто-добор по стилю референсов — только как fallback, с пометкой).

### 2. [major] У специалиста нет сценария входящей прямой заявки — зеркала главной клиентской воронки
- **Файл**: `ux-specialist.md` (весь документ).
- **Суть**: клиентский Сценарий 1 («заявка за 3 минуты») — центральная воронка спеки («лента = воронка»), но на стороне специалиста прямая заявка существует только как строка `lead_new` в матрице уведомлений и экран S16 «Чат». Нет флоу: уведомление → просмотр заявки → первый ответ; при том что метрика «медиана первого ответа < 4 ч» уже заведена в А.6 events-notifications.
- **Исправление**: добавить в `ux-specialist.md` сценарий (или подраздел Сценария 4) «Входящая заявка»: точки входа (Telegram/push/центр), карточка заявки в чате, целевое время первого ответа, точки отказа (заявка ночью, «не принимаю заказы» включён случайно), пусто/офлайн.

### 3. [major] Словарь статусов отклика рассинхронизирован в трёх местах
- **Файлы**: `ux-specialist.md` §Сценарий 3, шаг 6 («просмотрен», «в чате», «выбран другой»); `schema.prisma` `BriefResponseStatus` (SENT/SHORTLISTED/DECLINED/ACCEPTED); `events-notifications.md` §А.4 `brief_response_status_changed` (viewed|shortlisted|hidden|chat_started|hired).
- **Суть**: UI обещает статусы «просмотрен» и «выбран другой», которые схема не хранит (нет VIEWED; «выбран другой» невыразим — есть только DECLINED). Реестр событий использует третий набор значений. Специалист не получит статусов, которые ему обещаны.
- **Исправление**: единый словарь. Предложение: `SENT → VIEWED → SHORTLISTED → ACCEPTED / DECLINED / HIDDEN`; «выбран другой» — производное от `brief_closed(reason=hired)` для остальных откликов. Добавить недостающие значения в `BriefResponseStatus`, привести enum события к ним, поправить формулировки в ux-specialist.

### 4. [major] События заказа/отзыва в ux-client не совпадают с каноническим реестром и не покрыты нормализацией А.7
- **Файлы**: `ux-client.md` §Сценарий 4, блок «События аналитики»; `events-notifications.md` §А.1.6–А.1.7, §А.7.
- **Суть**: ux-client использует `order_terms_proposed`, `order_confirmed_mutual`, `order_status_changed`, `order_delivery_proposed/accepted`, `order_revision_requested`, `order_autocompleted`, `checkpoint_added`, `review_submitted {rating_quality…}`. Канон: `order_create_started`, `order_confirm_requested`, `order_confirmed`, `order_delivered`, `order_returned_for_rework`, `order_completed {confirmation}`, `order_checkpoint_added`, `review_submitted {score_*}`. §А.7 нормализует только `otp_*` и дайджест — весь заказный словарь клиентского драфта повисает.
- **Исправление**: заменить в `ux-client.md` §4 имена и свойства на канонические; дополнить §А.7 таблицей соответствия (включая `order_confirmed_mutual → order_confirmed`, `order_autocompleted → order_completed(confirmation=auto)`, `rating_* → score_*`).

### 5. [major] api-contract использует собственные имена событий, ломающие воронки реестра
- **Файлы**: `api-contract.md` (аналитика у процедур, §20); `events-notifications.md` §А.0 п.8, §А.6.
- **Суть**: реестр объявлен единственным («строковых литералов имён в коде нет»), но контракт пишет: `otp_requested`/`otp_verified` (канон `auth_otp_*`), `case_saved` (канон `item_saved`), `review_created` (канон `review_submitted` — ★-шаг воронки!), `user_registered` (канон `auth_completed`), `order_state_changed` вместо гранулярных `order_*`, `case_viewed`, `brief_created` (канон `brief_published`), `checkpoint_added`. Воронки §А.6 по этим именам не соберутся.
- **Исправление**: в `api-contract.md` привести все имена к реестру `packages/core/analytics/events.ts` и переписать сводку §20 каноническими именами (`… → item_saved / lead_submitted → order_confirmed → order_completed → review_submitted`).

### 6. [major] «Заявка» не определена как сущность: нет раскрытия телефона и вложений первого сообщения
- **Файлы**: `ux-client.md` §Сценарий 1, шаги 6–8; `api-contract.md` §12 `chat.start`, §7 `profiles.publicBySlug`; `events-notifications.md` §А.1.5.
- **Суть**: (а) спека требует «телефон скрыт ДО заявки» — т.е. после заявки раскрывается; ux-client обещает «телефон специалиста раскрыт», реестр имеет серверное `lead_phone_revealed {lead_id}` — но в API нет ни одного места, где телефон возвращается (publicBySlug — «ни при каких условиях», в `chat.threads`/`peer` поля нет), и не определено, что такое `lead_id`. (б) Модал заявки позволяет «прикрепить фото/референс», а `chat.start` принимает только `firstMessage: string`.
- **Исправление**: зафиксировать в `api-contract.md` §12: заявка = `chat.start` (lead_id = threadId); добавить `attachments?: uploadId[]` в `chat.start`; добавить раскрытие телефона участникам треда (поле `peer.phone` в `chat.threads`/`chat.messages` при существующем треде) + серверное событие `lead_phone_revealed`.

### 7. [major] Обещания «редактирование отзыва 72 ч» и «публичный ответ на отзыв» не поддержаны схемой и API
- **Файлы**: `ux-client.md` §Сценарий 4, шаг 6; `ux-specialist.md` §Сценарий 4, шаг 6 и S19; `schema.prisma` (Review); `api-contract.md` §14.
- **Суть**: ux-client обещает клиенту окно редактирования 72 ч (`review_edited` в событиях), ux-specialist — публичный ответ специалиста на отзыв (экран S19). В Review нет поля ответа, в API нет `reviews.update` и `reviews.reply`.
- **Исправление**: либо добавить `reviews.update` (гард ≤72 ч, только автор, пересчёт агрегата) и `Review.replyText/replyAt` + `reviews.reply` (owner-специалист, контакт-детект §4), либо вычеркнуть оба обещания из ux-драфтов. Решение зафиксировать — сейчас три документа противоречат друг другу.

### 8. [major] SLA спора: пользователю обещаны «2 рабочих дня», процесс арбитража рассчитан на бóльшее
- **Файлы**: `ux-client.md` §Сценарий 4, шаг 7; `events-notifications.md` §Б.3 `dispute_update (opened)`; `ux-agency-admin.md` §Б4, шаги 1–2.
- **Суть**: клиенту и в UI, и в Telegram-шаблоне обещано «ответим/решение в течение 2 рабочих дней», но по Б4 у второй стороны есть 48 ч на позицию и ещё ≤72 ч на решение после получения обеих позиций — до 5 дней. Обещание системно нарушается — прямой удар по «честность = позиционирование».
- **Исправление**: единая формулировка во всех трёх местах: «решение в течение 3 дней после того, как обе стороны изложат позиции (на это даётся 48 часов)». Поправить текст шаблона в Б.3 и шаг 7 ux-client.

### 9. [major] ux-specialist: нет блоков «офлайн/пусто/ошибка» в сценариях 3–5
- **Файл**: `ux-specialist.md` §Сценарии 3, 4, 5.
- **Суть**: требование задачи — покрытие пустот/ошибок/офлайна в каждом сценарии. В ux-client это отдельный блок в каждом сценарии + сквозной Сценарий 5. В ux-specialist пусто покрыто точечно (портфолио, лента брифов, нулевая статистика), но офлайн и ошибки для отклика на бриф, ведения заказа и статистики не описаны (обрыв при отправке отклика, конфликт статусов заказа при одновременных нажатиях, статистика без сети).
- **Исправление**: добавить в каждый сценарий блок «Офлайн / пусто / ошибка» по образцу ux-client: отклик → outbox с ретраем; переходы заказа → optimistic locking + «статус уже изменился» (согласуется с `expectedState` из api-contract §2); статистика → кэш с меткой свежести.

## Что в порядке (проверено, правок не требует)

- **Регистрация в момент ценности** — нарушений нет ни в одном драфте: гостевая лента/кейсы/профили, локальное гостевое сохранение с миграцией, OTP на сохранении/заявке/брифе/клейме организации, жалоба гостю без регистрации (осознанно). Единственная шероховатость — формулировка инварианта (находка 19).
- **Мобильная эргономика** — 44px/зона большого пальца/bottom sheets/числовая клавиатура последовательно проведены в клиенте и специалисте; десктоп-консоль модератора корректно оформлена как осознанное исключение с mobile-путём для действий первой линии.
- **Запрет кредитных/процентных механик** — подтверждён во всех драфтах, включая арбитраж (Б4 прямо проговаривает роль платформы) и B2B-планы (А3: «никаких комиссий, только подписочная витрина»).
- **Отзыв только по завершённому заказу** — инвариант непротиворечиво проведён через клиентский Сценарий 4, специалистский Сценарий 4, исходы арбитража Б4 (отменённый заказ = отзывов нет) и антифрод Б6.
