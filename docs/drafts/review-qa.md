# ATELIER — QA-ревью драфтов: реестр edge-cases и противоречий

Статус: результат ревью. Проверены: `ux-client.md`, `ux-specialist.md`, `ux-agency-admin.md`,
`schema.prisma`, `data-model-notes.md`, `api-contract.md`, `events-notifications.md`
против `04-product-spec.md`, `03-decisions.md`, `00-prompt-analysis.md`.

Формат находки: серьёзность → файл+раздел → проблема → ожидаемое поведение → где живёт исправление
(core-правило `packages/core` / БД-констрейнт / UI).

## 0. Проверено и закрыто драфтами (находок нет)

- **Отзыв без заказа** — закрыт двумя слоями: `Review.orderId @unique` + FK на Order (БД) и
  `order.state === COMPLETED`, `author === order.clientId` в core (`api-contract §14`,
  `data-model-notes §2`). Обходных процедур в API нет, импорта внешних отзывов нет (03/5).
- **Повторный отзыв на тот же заказ** — `orderId @unique`, повтор → `CONFLICT`. Повторные отзывы
  той же пары по *разным* заказам легитимны (повторный клиент) и покрыты velocity-правилом
  (≥3 за 90 дней → `ModerationItem`).
- **Гость сохраняет и не завершает регистрацию** — UX-сторона спроектирована честно
  (`ux-client.md` сц. 3): локальное сохранение, тост «на этом устройстве», бейдж при возврате,
  данные не удаляются до подтверждения сервера. Дыра только в API-контракте — см. находку №11.
- **OTP: базовая защита от перебора** — `auth.requestOtp` 1/мин, 5/час на телефон, 10/сутки на IP;
  `verifyOtp` 5 попыток на challenge с аннулированием; существование аккаунта не раскрывается.
  Остаточные мелочи — находка №26.

## BLOCKER

### 1. Арбитраж обещает «отзывы обеим сторонам» — модель отзывов односторонняя
- **Где**: `ux-agency-admin.md` Б4 (таблица исходов: «Обе стороны могут оставить отзыв как обычно»,
  «Право второй стороны на свой отзыв сохраняется») ↔ `schema.prisma` `Review` (1:1 к заказу,
  автор = клиент) ↔ `api-contract.md` §14 (`author === order.clientId`, «специалист клиента
  в MVP не оценивает»).
- **Проблема**: Б4 спроектирован под двусторонние отзывы, которых нет ни в схеме, ни в API, ни в спеке.
  Реализация «как написано» потребует ломать `orderId @unique` и всю модель репутации.
- **Ожидаемое поведение**: в MVP отзыв — только клиентский. Исход арбитража «завершить» открывает
  клиенту стандартное окно отзыва (90 дней от `completedAt`, проставленного арбитражем).
- **Исправление**: переписать Б4 (убрать «обе стороны»/«свой отзыв второй стороны»); модель не трогать.
- **Слой**: текст драфта; инвариант остаётся в БД (`@unique`) + core.

### 2. PRO→Free с 12 опубликованными кейсами — поведение не определено нигде
- **Где**: `api-contract.md` §8 `cases.submit` (лимит Free = 5 published), §18 (истечение
  `Entitlement`), `events-notifications.md` Б3 `pro_status expiring` («профиль и кейсы останутся
  на месте, но публикация новых кейсов сверх 5 станет недоступна» — единственное место, где
  поведение вообще упомянуто, и то в тексте уведомления), `data-model-notes.md` §2.
- **Проблема**: воркер, гасящий истёкший PRO (`@@index([status, expiresAt])` под это и заведён),
  не имеет правила для контента сверх лимита. Любое «само собой» решение (авто-скрытие 7 кейсов)
  уничтожает контент и доверие; отсутствие правила = недетерминированное поведение core-лимита.
- **Ожидаемое поведение** (предложение, согласуется с текстом `pro_status`): **grandfathering** —
  существующие 12 кейсов остаются `PUBLISHED`; публикация новых блокируется, пока
  `count(published) ≥ max` (т.е. вернуться к публикациям можно, заархивировав до 4);
  `cases.myList.slots` и `billing.myEntitlements.usage` показывают `used: 12, max: 5` честно,
  UI — плашка «кейсы сверх лимита Free остаются, но новые — в PRO».
- **Исправление**: зафиксировать правило в `03-decisions.md` + `data-model-notes §2` (лимит —
  предикат публикации, не инвариант хранения); проверка остаётся в `cases.submit`.
- **Слой**: core-правило (`core/entitlements.check`) + UI (`slots`, апселл). БД-констрейнт не нужен.

## MAJOR

### 3. Вес отзыва при авто-подтверждении: обещано понижение, формула его не знает, схема не хранит признак
- **Где**: `ux-client.md` сц. 4 шаг 5 и таблица отказов («вес отзыва ниже… при авто-подтверждении»),
  `events-notifications.md` А.1.7 (`review_submitted` без `was_autocompleted`; в `ux-client` prop был) ↔
  `api-contract.md` §14 п.5 (weight = 0.7 + 0.15 верификация + 0.15 чек-поинты — авто-подтверждения нет) ↔
  `schema.prisma` `Order` (`confirmedAt` проставляется и клиентом, и воркером — авто/ручное неразличимо
  постфактум; комментарий это прямо говорит).
- **Проблема**: заявленная антифрод-контрмера (00/1.2) не реализуема: формула не учитывает
  авто-подтверждение, а после завершения по данным нельзя понять, было ли оно автоматическим.
  Пометка «подтверждено автоматически» в UI (ux-client шаг 5) тоже не строится.
- **Ожидаемое поведение**: воркер авто-подтверждения оставляет `confirmedAt = null` (заполняет только
  `completedAt`) ИЛИ добавляется `Order.autoConfirmed Boolean`; формула веса получает слагаемое
  (например, −0.15 при авто); `review_submitted` получает `was_autocompleted`.
- **Слой**: БД (поле/семантика `confirmedAt`) + core (`core/reputation` формула) + UI (пометка на заказе).

### 4. Спор: «возврат в работу» есть в UX, но отсутствует в state machine
- **Где**: `ux-client.md` сц. 4 шаг 7 («Исходы: возврат в „в работе“, „завершён“, „отменён“») и
  mermaid (`Спор → Доработка → E`) ↔ `data-model-notes.md` §1 и `api-contract.md` §15
  (`DISPUTED → COMPLETED | CANCELLED` — только два исхода) ↔ `ux-agency-admin.md` Б4 (тоже два исхода
  + «завершить с блокировкой отзыва»).
- **Ожидаемое поведение**: «доработка» — разумный исход арбитража (работа велась, но не доделана).
  Добавить переход `DISPUTED → IN_PROGRESS` (арбитраж, сброс `deliveredAt/autoConfirmAt`) в
  state machine, матрицу `orders.transition`/`moderation.decide` и mermaid всех трёх документов —
  либо убрать исход из ux-client. Предпочтительно первое.
- **Слой**: core (матрица переходов) + правка драфтов.

### 5. Исход Б4 «отзыв уже оставлен и является шантажом» недостижим через спор
- **Где**: `ux-agency-admin.md` Б4 (исход «Завершить + заблокировать отзыв») ↔ state machine:
  отзыв существует только после `COMPLETED` (терминален), а спор открывается только из
  `IN_PROGRESS | DELIVERED` — т.е. к моменту существования отзыва спор открыть уже нельзя.
- **Ожидаемое поведение**: блокировка отзыва-шантажа — это не арбитраж спора, а модерация отзыва по
  жалобе: `moderation.report(REVIEW)` → `moderation.decide(REJECT)` → `hiddenAt` + пересчёт
  агрегатов — этот путь уже есть в API. Из Б4 исход убрать/переадресовать в Б3.
- **Слой**: текст драфта; механика уже существует (`Review.hiddenAt` + пересчёт).

### 6. Смена номера телефона — флоу отсутствует; переизданные номера
- **Где**: нигде (проверены все драфты). `schema.prisma`: `phone @unique` — первичный идентификатор
  входа; `api-contract.md` §6 имеет только `auth.linkPhone` для Google-аккаунтов без телефона.
- **Проблема**: смена SIM — частый кейс на рынке; пользователь с новым номером теряет аккаунт
  (портфолио, репутацию, заказы). Обратный риск: оператор переиздал номер → новый владелец получает
  OTP и входит в чужой аккаунт (чаты, раскрытые телефоны).
- **Ожидаемое поведение**: `auth.changePhone` — из активной сессии: OTP на новый номер
  (`CONFLICT`, если занят), уведомление на старые каналы (Telegram/in-app) с окном отката 72 ч;
  запись в audit log (см. №14). Для переизданных номеров: при OTP-входе в аккаунт с
  `lastSeenAt` старше N месяцев — дополнительная проверка (подтверждение через привязанный Telegram,
  если есть) — минимум зафиксировать риск в 03-decisions как осознанный.
- **Слой**: core/API (новая процедура + rate limit) + UI (настройки) + audit log.

### 7. Удаление аккаунта пользователем — отсутствует; активные заказы не разрулены
- **Где**: нигде. `api-contract.md` §15 — только `admin.banUser`; `schema.prisma` — `User.deletedAt`
  есть, но пользовательской процедуры нет.
- **Проблема**: юридически обязательный флоу (перс. данные; юр. база — 00/§2). Без правил: что с
  активными заказами, отзывами, phone-уникальностью (номер «занят» удалённым аккаунтом навсегда),
  совместными кейсами.
- **Ожидаемое поведение**: `account.delete` — блокируется при заказах в
  `AGREED | IN_PROGRESS | DELIVERED | DISPUTED` («завершите или отмените заказы»); soft-delete +
  анонимизация PII (displayName → «Удалённый пользователь», avatar/phone очищаются, phone —
  в хэш для антифрода, unique освобождается); отзывы и завершённые заказы остаются (репутация
  специалистов неприкосновенна), кейсы удалённого автора скрываются, ACCEPTED-коллаборации остаются
  в чужих кейсах как «участник удалил аккаунт». Окно отмены 7 дней.
- **Слой**: core-правило (предикаты состояния заказов) + БД (анонимизация, освобождение unique) + UI.

### 8. Повторный клиент не может открыть второй заказ, пока первый активен
- **Где**: `api-contract.md` §12 `chat.start` («существует тред пары → возвращается он же») +
  §13 `orders.create` («уже есть активный заказ в треде → CONFLICT»).
- **Проблема**: у пары без брифа тред единственный → второй параллельный проект (дизайн квартиры
  идёт, клиент заказывает ещё дачу) невозможен. «% повторных клиентов» — публичная витринная метрика,
  флоу повторного заказа должен быть беспрепятственным.
- **Ожидаемое поведение**: разрешить несколько активных заказов в треде (карточка статуса в чате
  становится списком/переключателем); `CONFLICT` заменить на мягкий UI-вопрос «создать ещё один
  заказ?». Антифрод и так смотрит velocity пары.
- **Слой**: core (снять ограничение) + UI чата (несколько карточек заказов).

### 9. OrgMembership: схема противоречит UX по статусам и видимости метки
- **Где**: `schema.prisma` `OrgMembership` (`isConfirmed Boolean`, комментарий «публичная подпись
  показывается только после подтверждения») ↔ `ux-agency-admin.md` А1 шаг 4 (метка `declared`
  показывается СРАЗУ с тултипом «указано специалистом, не проверено»), А1 шаг 5 и А3 п.1
  (статусы `declared/confirmed/left/rejected`, `period_from/period_to`, «историю храним»).
- **Проблема**: в MVP подтверждающей стороны нет (owner появляется после claim) — с булевым
  `isConfirmed=false` и «показом только после подтверждения» метка «работает в X» не заработает вовсе;
  `left`/история непредставимы, «работал в X (2024–2026)» (А3 п.5) не построить.
- **Ожидаемое поведение**: `status MembershipStatus (DECLARED|CONFIRMED|LEFT|REJECTED)` +
  `periodFrom/periodTo`; `@@unique([organizationId, userId])` пересмотреть (повторное трудоустройство
  в ту же org после LEFT) — например, unique только по активным. UI: declared виден с тултипом.
- **Слой**: БД (enum + поля) + UI (тултип обязательный).

### 10. Черновик кейса на двух устройствах: last-write-wins против обещания «черновик не теряется никогда»
- **Где**: `api-contract.md` §8 `cases.update` (частичный patch, никакого version-контроля) ↔
  `ux-client.md` инвариант 5 и `ux-specialist.md` сквозной принцип («обрыв не должен терять работу»).
- **Проблема**: телефон днём + ноутбук вечером — типовой паттерн персоны. Автосейв с debounce 2 с
  с двух устройств молча перетирает поля; `reorderImages`/`removeImage` конфликтуют жёстче.
- **Ожидаемое поведение**: optimistic concurrency по образцу заказов (`expectedState` уже есть в §13):
  `cases.update` принимает `baseUpdatedAt/version`, расхождение → `PRECONDITION_FAILED`
  «Черновик обновлён на другом устройстве» + UI-выбор «взять свежую версию».
- **Слой**: core/API (precondition) + UI (диалог конфликта). БД: `updatedAt` уже есть.

### 11. Миграция гостевой коллекции: событие есть, процедуры в API нет
- **Где**: `ux-client.md` сц. 3 шаги 2–4, `events-notifications.md` А.1.3
  (`guest_collection_migrated [S]`) ↔ `api-contract.md` §9 — только `saveCase` поштучно.
- **Проблема**: ключевой шаг «регистрации в момент ценности» без контракта. Поштучный `saveCase`
  с клиента после OTP — неатомарно и без серверного события; кейс из локального сохранения мог быть
  удалён/скрыт к моменту миграции.
- **Ожидаемое поведение**: `collections.importGuestSaves — mutation { items: [{caseId, caseImageId?}],
  idempotencyKey }` → создаёт коллекцию-дефолт, молча пропускает несуществующие/скрытые кейсы,
  возвращает `{imported, skipped}`, пишет `guest_collection_migrated` серверно. Клиент чистит
  localStorage только после ответа (ux уже требует).
- **Слой**: API/core + UI (бейдж «несинхронизированные»).

### 12. Совместный кейс: редактирование, удаление, выход соавтора — правила не определены
- **Где**: `schema.prisma` `CaseCollaborator` (нет выхода после ACCEPTED), `api-contract.md` §8
  (`cases.update/delete` — только owner; `respondCollaboration` — единственная реакция),
  `ux-specialist.md` сц. 2 шаг 6.
- **Проблема/пробелы**: (а) соавтор не может убрать чужой кейс из своего портфолио после ACCEPTED
  (поссорились, атрибуция спорная); (б) автор удаляет/архивирует кейс — соавторы не уведомляются,
  контент молча исчезает из их витрин; (в) не зафиксировано, что кейс не считается в лимит Free
  соавтора (по коду `cases.submit` считает только `authorId` — правильно, но нигде не проговорено).
- **Ожидаемое поведение**: редактирует/удаляет только автор; соавтор в любой момент может выйти
  (`cases.leaveCollaboration` → status REVOKED, кейс уходит из его профиля, автору — уведомление);
  `delete/unpublish/archive` кейса → `Notification` всем ACCEPTED-соавторам; лимит Free — только
  у автора (зафиксировать в data-model-notes §2).
- **Слой**: core (права) + БД (`CollaboratorStatus.REVOKED`) + UI + правка notes.

### 13. Модерация: «вернуть на доработку» есть в UX, невозможен в API/схеме
- **Где**: `ux-agency-admin.md` Б1 шаг 4b (`request_changes` — центральный исход конвейера,
  «слот из 3 не сгорает», возврат к тому же модератору) ↔ `schema.prisma` `ModerationStatus`
  (PENDING|APPROVED|REJECTED|ESCALATED) и `api-contract.md` §15 `moderation.decide`
  (APPROVE|REJECT|ESCALATE).
- **Ожидаемое поведение**: decision `REQUEST_CHANGES`: кейс → `DRAFT` c `rejectReason`
  (плашка «нужно поправить»), `ModerationItem` → статус `CHANGES_REQUESTED`; повторный submit
  создаёт item с `assigneeId` прежнего модератора. Слот премодерации инкрементится только на APPROVE
  (сверить с №22 — «3-й одобренный»).
- **Слой**: БД (enum) + core (побочные эффекты decide) + консоль модератора.

### 14. Audit log заявлен обязательным — в схеме его нет
- **Где**: `ux-agency-admin.md` преамбула («каждое действие модератора — в неизменяемый журнал»,
  «каждый просмотр документов — в audit log» Б5) ↔ `schema.prisma` — модели нет;
  `api-contract.md` §15 пишет `admin_action` в `AnalyticsOutbox` — это доставка в PostHog,
  не неизменяемый журнал (и не покрывает просмотры документов).
- **Ожидаемое поведение**: `model AuditLog { actorId, action, entityType, entityId, payload Json,
  createdAt }` — append-only (без update/delete в коде), пишется в транзакции с действием;
  просмотр документа верификации — тоже действие.
- **Слой**: БД + core (запись в каждой модераторской/админской мутации и в `moderation.item`
  при открытии документов).

### 15. Жалобы гостей: Б3 разрешает, API и схема — нет
- **Где**: `ux-agency-admin.md` Б3 («для гостя — тоже, rate limit по IP») ↔ `api-contract.md` §15
  `moderation.report` (права: client, specialist) ↔ `schema.prisma` `Report.reporterId` (обязательный FK).

### 17. VerificationKind: нет типа org_claim

### 18. Автоудаление документов верификации через 30 дней — нет носителя
- **Где**: `ux-agency-admin.md` Б5 (обязательное требование + комплаенс-событие
  `verification_docs_purged`) ↔ `schema.prisma` `Verification` и `api-contract.md` §7 — ни поля,
  ни воркера.
- **Исправление**: `Verification.docsPurgedAt` + `documentLast4`; cron-воркер BullMQ: `reviewedAt +
  30 дней` → удалить объекты в R2, очистить `documents`, событие в outbox.
- **Слой**: БД + воркер.

### 19. Редактирование отзыва «окно 72 ч» — нет процедуры и полей
- **Где**: `ux-client.md` сц. 4 шаг 6 («редактирование — окно 72 ч, дальше только через поддержку»)
  ↔ `api-contract.md` §14 (нет `reviews.update`), `schema.prisma` `Review` (нет `editedAt`).
- **Исправление**: либо `reviews.update` (≤72 ч от `createdAt`, пересчёт `ReviewAggregate`
  в транзакции, `editedAt`, событие `review_edited` — оно уже есть в ux-client), либо вычеркнуть
  обещание из UX. Предпочтительно первое: право исправить отзыв снижает споры.
- **Слой**: API/core + БД (поле) + UI.

### 20. Пометка `via_arbitration` на отзыве — поля нет
- **Где**: `ux-agency-admin.md` Б4 («пометка в данных нужна аналитике и антифроду») ↔
  `schema.prisma` `Review` — поля нет.
- **Исправление**: `Review.viaArbitration Boolean @default(false)` (или `source enum`), проставляется
  core при отзыве по заказу, завершённому решением арбитража.
- **Слой**: БД + core.

### 21. Расписание напоминаний авто-подтверждения — три разные версии
- **Где**: `ux-client.md` сц. 4 шаг 5 («день 1, день N−1») ↔ `ux-specialist.md` откр. вопрос 2
  («напоминания на 3-й и 6-й день») ↔ `events-notifications.md` Б1/Б3 (T-48 и T-24 от
  `autoConfirmAt`) — последний сам же флагует проблему в откр. вопросе 4.
- **Исправление**: канон — T-48/T-24 от `autoConfirmAt` (не зависит от N, N остаётся конфигом);
  поправить оба ux-драфта; зафиксировать N=7 в `03-decisions.md`.
- **Слой**: воркер уведомлений + правка драфтов.

### 22. Trust-tier: «3-й approve подряд» vs «3-й одобренный»
- **Где**: `api-contract.md` §15 («3-й approve подряд») ↔ `ux-agency-admin.md` Б1 4a
  («3-й одобренный кейс») + 4c («отклонённый не сжигает слот из 3»).
- **Исправление**: канон — счётчик одобренных кейсов (reject не сбрасывает и не сжигает);
  убрать «подряд» из контракта.
- **Слой**: core (счётчик) + правка контракта.

### 23. Лимит откликов Free: 5/мес vs 10/мес
- **Где**: `ux-specialist.md` откр. вопрос 1 (предлагает 5/мес) ↔ `api-contract.md` §11 и §21
  (Free = 10/мес как seed-дефолт).
- **Исправление**: одно число, зафиксировать в `03-decisions.md` (значение живёт в
  `Plan.maxBriefResponsesMonthly`, менять без миграции). Дефолт-предложение: 10 — щедрее на холодном
  старте, ужесточить проще, чем ослабить.
- **Слой**: seed БД + решение продукта.

### 24. Фото в кейсе: «до 30» vs «до 20»
- **Где**: `ux-specialist.md` сц. 2 шаг 1 (мультивыбор до 30) ↔ `api-contract.md` §8
  `cases.attachImage` («В кейсе до 20 фото»).
- **Исправление**: одно число в обоих местах (предложение: 20 — достаточно, дешевле по хранению/LCP).
- **Слой**: core-лимит + UI мастера.

### 25. SLA спора: «2 рабочих дня» vs 48 ч на позицию + 72 ч на решение
- **Где**: `ux-client.md` сц. 4 шаг 7 и `events-notifications.md` Б3 `dispute_update` («обычно
  в течение 2 рабочих дней») ↔ `ux-agency-admin.md` Б4 (48 ч на ответ второй стороны, затем ≤72 ч
  решение — суммарно до 5 суток).
- **Исправление**: единый честный текст: «вторая сторона отвечает до 48 ч, решение — до 3 дней после
  этого»; либо сократить внутренние SLA. Обещание в UI не должно быть меньше внутреннего SLA.
- **Слой**: тексты уведомлений + UI спора.

### 26. OTP: не задан TTL challenge, нет IP-лимита на verify
- **Где**: `api-contract.md` §3, §6 (есть «Код устарел», но TTL не зафиксирован; `verifyOtp`
  лимитирован только по challenge).
- **Исправление**: TTL challenge = 10 мин; `verifyOtp` дополнительно 20/час на IP (распределённый
  перебор через множество challenge'ей); после 3 подряд аннулированных challenge на один номер —
  кулдаун 1 час.
- **Слой**: core/rate limits (Redis).

### 27. Таймзона пользователя: пайплайн ссылается на поле, которого нет
- **Где**: `events-notifications.md` Б0/Б5 («тихие часы 22:00–08:00 локального времени», «digest…
  таймзона пользователя, дефолт Asia/Bishkek») ↔ `schema.prisma` `User` — поля timezone нет.
  Также «N дней» авто-подтверждения: `autoConfirmAt` хранится в UTC, а `{auto_confirm_date}` в текстах
  должен рендериться в местном времени (иначе ±день у границы суток).
- **Исправление**: MVP — константа `Asia/Bishkek` для всех (КР — одна зона, без DST): тихие часы,
  digest-cron и форматирование дат уведомлений считать в ней; `User.timezone` добавить аддитивно
  в Фазе 2 (KZ/UZ). Убрать из Б5 слова «таймзона пользователя» либо добавить поле сразу.
- **Слой**: воркер уведомлений (форматирование) + решение по полю в БД.

### 28. Отмена заказа после «сдан»: путь есть только через доработку/спор — зафиксировать явно
- **Где**: `data-model-notes.md` §1 и `api-contract.md` §13 (cancel только из
  DISCUSSION|AGREED|IN_PROGRESS — корректно) ↔ `ux-client.md` сводная таблица экран 14 («кнопки
  подтверждений, спор/отмена» без оговорки о статусе).
- **Ожидаемое поведение**: прямой cancel из DELIVERED запрещён сознательно (иначе клиент обнуляет
  сданную работу в обход возврата/спора) — это правильно, но нигде не проговорено как решение.
  В DELIVERED UI показывает только «Принять / Есть замечания / Открыть спор». Отмена «после сдан» =
  `return_to_work` → `cancel` или `DISPUTED → CANCELLED` арбитражем.
- **Слой**: core уже верен; правка UI-таблицы ux-client + пункт в data-model-notes.

### 29. Гонка на лимите Free при конкурентном submit
- **Где**: `data-model-notes.md` §2 («проверка в той же транзакции… уровень изоляции достаточен») —
  утверждение неверно: `count + update` под READ COMMITTED допускает двойную публикацию
  (два сабмита читают count=4, оба публикуют → 6). `idempotencyKey` опционален и не спасает
  от разных ключей.
- **Исправление**: advisory lock по `userId` (`pg_advisory_xact_lock`) вокруг count+update в
  `cases.submit` (и аналогично счётчик откликов в `briefs.respond`, redeem промокода уже с
  блокировкой строки).
- **Слой**: core/транзакция.

### 30. Заказ между двумя специалистами: роли client/specialist в паре не определяются «ролями треда»
- **Где**: `api-contract.md` §13 `orders.create` («клиент/специалист определяются ролями в паре
  треда») — ломается, когда обе стороны `SPECIALIST` (дизайнер нанимает фотографа; §11 явно допускает
  «specialist-как-клиент» в брифах).
- **Исправление**: роль в заказе — из контекста, не из `User.role`: заказчик = автор брифа /
  инициатор заявки на чужой профиль; хранить в Order как есть (`clientId/specialistId` — про роль
  в заказе, не глобальную). Уточнить формулировку контракта.
- **Слой**: core (правило определения сторон) + правка контракта.
